# Ask-mode role replacement

Use this procedure when the Chief of Staff proposes replacing a subordinate in ask mode. The user who selects this policy authorizes the stated default for that staffing decision. The timer runs in an active coordinator session. Other tickets may continue while the affected handoff waits.

1. Checkpoint the proposal under a unique decision ID with the ticket, incumbent invocation, proposed successor and reason. Deliver a nonblocking user-visible notice identifying the decision and the 60-second default. For example, “R17: I propose replacing the CI worker on ticket 24 because the same runner fault recurred after feedback. Reply to approve, veto or discuss. After 60 seconds of silence, I will proceed.” Start timing at successful notice delivery and persist its Unix timestamp in seconds. If delivery fails, retry before starting the clock.
2. Schedule an interruptible host wake-up for the deadline. If the host supports a background command, it can run `scripts/replacement_window.py` using a structured JSON request on stdin with `{"action":"wait","notified_at":<delivery timestamp>}`. Reuse the original timestamp across wake-ups. Handle incoming messages immediately while the wake-up is pending. If the host has only a blocking confirmation dialog, use a normal notice and a timed wake-up instead. A host without a timer or background execution evaluates the deadline when the coordinator next runs.
3. Before acting, collect user messages received since the notice, including messages queued while the host was asleep. Resolve using the helper with `{"action":"resolve","notified_at":<delivery timestamp>,"replies":[...]}`. Each reply carries its host receipt timestamp in `received_at` and a `kind` of `approve`, `veto` or `other`. Use receipt order. An approval or veto must refer clearly to this decision. Any question, pause, unrelated reply or uncertain attribution interrupts the silence and requires clarification. Include replies received at the deadline and any newer user direction before dispatch. If the inbox history is incomplete after a restart, deliver a fresh notice.
4. Persist the outcome against the decision ID. `pending` keeps the original deadline. `needs_clarification` suspends the default until the user resolves the question or the coordinator delivers a fresh proposal. `vetoed` retains the incumbent. `approved` and `timeout_default` allow the proposed handoff; record which occurred. The coordinator owns this transition exclusively.
5. Before dispatch or recovery, confirm the same ticket, incumbent and successor proposal still apply. Reissue a changed proposal. For an authorized handoff, checkpoint the incumbent's work, release its exclusive claim, dispatch the successor and record its invocation ID. On retry reconcile live invocations and the claim before creating another worker. Record a dispatch failure separately from the window outcome. Preserve existing repository, tool and delivery authorizations.
